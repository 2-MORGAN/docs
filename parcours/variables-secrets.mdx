Vous allez équiper l'application mon-appli de ses secrets, du runtime jusqu'à la production, sans jamais exposer de valeur sensible.

## Avant de commencer

- Votre application mon-appli est déployée et vous connaissez son identifiant, ici `123` à titre d'exemple. Retrouvez le vôtre dans l'URL de sa fiche. Ce même nombre désigne le projet dans les commandes de coffre.
- Vous êtes propriétaire, membre ou administrateur du projet. Avec un rôle moindre, l'interface affiche le message `Votre rôle permet de consulter les noms des variables, sans les modifier.`
- La CLI est installée et connectée. Vérifiez avec `nimbus auth whoami`.
- Votre fichier `.env` local est prêt. Il contient une variable par ligne au format `NOM=valeur`, en texte UTF-8, et pèse au maximum 64 Kio.

## Faire

<Tabs>
<Tab title="Interface">

<Steps>
<Step title="Ajoutez la clé API au runtime">
Dans la fiche de mon-appli, ouvrez la section **Configuration**, puis **Variables**. Saisissez `API_URL` comme nom de variable et collez l'adresse de votre API comme valeur. Cliquez sur **Ajouter**. Le message `API_URL ajoutée` confirme la création et chaque écriture redémarre l'application.
</Step>
<Step title="Repérez les variables gérées">
Les clés posées par Nimbus portent la mention **Gérée par Nimbus · Lecture seule**. Vous pouvez les lire mais pas les modifier depuis cet onglet. Si votre rôle ne permet pas l'écriture, vous voyez le message `Votre rôle permet de consulter les noms des variables, sans les modifier.`
</Step>
<Step title="Partagez le fichier .env local">
Dans la section **Configuration**, ouvrez **Coffre de développement**. Le panneau `Secrets de développement de {projectName}` affiche l'état du fichier partagé, où `{projectName}` est le nom de votre projet. Cliquez sur **Télécharger le .env** pour récupérer la version partagée par votre équipe. Le fichier téléchargé contient vos secrets en clair : excluez-le de Git avec `.gitignore`. Pour publier une nouvelle version, choisissez votre fichier `.env`, cliquez sur **Enregistrer le fichier**, puis confirmez avec **Remplacer** dans le dialogue `Remplacer le fichier de développement ?`. Le contenu du fichier n’est pas affiché.
</Step>
<Step title="Publiez les secrets en production">
Dans la section **Configuration**, ouvrez **Coffre de production**. Avant le premier import, incluez dans votre fichier les variables existantes que l'application doit conserver. Choisissez votre fichier `.env.production` dans la zone **Importer un fichier .env**, cliquez sur **Importer**, puis confirmez avec **Confirmer l’import** dans le dialogue `Importer les variables de production ?`. Lisez l'avertissement `L’application redémarrera.`, puis validez. Si les variables affichées ne correspondent plus au coffre, cliquez sur **Resynchroniser**, puis confirmez avec **Confirmer la resynchronisation** pour les réappliquer, ce qui redémarre aussi l'application.
</Step>
</Steps>

</Tab>
<Tab title="CLI">

<Steps>
<Step title="Listez les variables du runtime">
```sh
nimbus services env list 123 --json
```
Elle renvoie la liste des variables de l'application `123`, sans leurs valeurs.
</Step>
<Step title="Préparez la valeur dans un fichier">
```sh
echo -n "https://api.example.fr" > ./url.txt
```
Elle écrit l'adresse dans `./url.txt` sans saut de ligne, car la CLI refuse les secrets passés en argument.
</Step>
<Step title="Créez la variable API_URL">
```sh
nimbus services env create 123 --key API_URL --value-file ./url.txt --json
```
Elle crée la variable et renvoie la clé créée, jamais la valeur. Chaque écriture redémarre l'application.
</Step>
<Step title="Consultez l'état du coffre de développement">
```sh
nimbus env status 123 --json
```
Elle renvoie l'état du coffre, dont le numéro de `version` attendu par la prochaine écriture.
</Step>
<Step title="Récupérez le fichier .env partagé">
```sh
nimbus env pull 123 --output .env --force
```
Elle écrit le contenu du coffre dans votre fichier `.env` local. Sans `--force`, la commande refuse d'écraser un fichier existant.
</Step>
<Step title="Publiez votre fichier .env">
```sh
nimbus env push 123 --dotenv-file .env --expected-version 0 --yes --json
```
Elle remplace tout le contenu du coffre par votre fichier et renvoie la nouvelle version. L'option `--yes` est obligatoire car l'écriture remplace tout le fichier. Gardez `--expected-version 0` si le coffre est encore vide, sinon reprenez la version rendue par le statut.
</Step>
<Step title="Consultez l'état du coffre de production">
```sh
nimbus prod-vault status 123 --json
```
Elle renvoie l'état du coffre de production, dont sa `version` et ses clés enregistrées.
</Step>
<Step title="Exportez le fichier de production">
```sh
nimbus prod-vault export 123 --output .env.production --force
```
Elle écrit le contenu du coffre dans `.env.production`, sans jamais l'afficher. Le fichier contient les valeurs en clair : excluez-le de Git.
</Step>
<Step title="Importez le fichier de production">
```sh
nimbus prod-vault import 123 --dotenv-file .env.production --expected-version 0 --yes --json
```
Elle remplace le coffre, applique les variables à l'application et renvoie les clés appliquées. L'option `--yes` est obligatoire car l'import remplace tout le coffre. Gardez `--expected-version 0` si le coffre est encore vide, sinon reprenez la version rendue par le statut. Chaque import redémarre l'application.
</Step>
<Step title="Resynchronisez si besoin">
```sh
nimbus prod-vault resync 123 --json
```
Elle réapplique les variables enregistrées dans le coffre et renvoie les clés appliquées. Chaque resynchronisation redémarre l'application.
</Step>
</Steps>

## Vérifier

- L'onglet **Variables** affiche `API_URL` avec la mention de sa date de mise à jour.
- Le panneau du coffre de développement indique un fichier enregistré, sa version et sa date de modification.
- Le **Coffre de production** affiche le badge **Enregistré** et la liste de ses clés, sans les valeurs.
- En CLI, `nimbus services env list 123 --json` inclut `API_URL` et les deux commandes `status` renvoient la même version que vos écritures.

## Si ça échoue

| Message exact | Cause | Geste |
| --- | --- | --- |
| `Cette variable est gérée par Nimbus.` | Vous touchez une clé posée par Nimbus pour l'identité de l'application | Vous ne pouvez pas la modifier ici ; passez par l'identité de l'application |
| `Utilise uniquement des majuscules, chiffres et underscores` | Le nom contient un caractère interdit | Renommez la clé en capitales, chiffres et soulignés uniquement |
| `Le fichier .env dépasse 64 Kio.` | Votre fichier dépasse la limite de 64 Kio | Allégez le fichier, puis réessayez l'enregistrement |
| `le coffre a été modifié ; rechargez avant de remplacer le fichier` | Quelqu'un a écrit dans le coffre entre-temps | Relisez le statut pour obtenir la version actuelle, puis réessayez |
| `Le fichier a été enregistré dans le coffre. Utilisez « Resynchroniser » pour terminer la mise à jour de l’application.` | L'import a enregistré le fichier mais Kubernetes ne l'a pas appliqué (erreur 502) | Cliquez sur **Resynchroniser** pour terminer la mise à jour |
| `Aucun fichier .env enregistré. Actualisez le coffre avant de réessayer.` | Vous exportez un coffre encore vide | Importez d'abord un fichier, puis exportez |

## Pour un agent

1. Demandez l'identifiant du service et le contenu fonctionnel des secrets. Attendez la réponse avant d'écrire.
2. Ne demandez jamais une valeur de secret en clair dans le chat si un fichier peut la porter. Faites passer les valeurs par `--value-file` ou `--dotenv-file`.
3. Créez `API_URL` avec `services env create`, puis constatez avec `services env list 123 --json`.
4. Lisez la `version` avec `env status` avant chaque `push`, et avec `prod-vault status` avant chaque `import`. Ne supposez jamais la version. Ajoutez `--yes` aux commandes `push` et `import`, car elles remplacent tout le fichier.
5. Après chaque écriture, rappelez que l'application redémarre et vérifiez avec la commande `status` correspondante.
6. N'affichez jamais un fichier `.env` ou `.env.production`, et excluez-les de Git avec `.gitignore`.
